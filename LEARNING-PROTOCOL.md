# System Design Learning Protocol

This document preserves the learning workflow across chat windows. Treat it as the source of truth for how System Design lessons are taught, assessed, reviewed, and tracked.

## Teaching approach
- Balanced, conversation-first learning: explain concepts interactively, then use selected external resources as reinforcement.
- Teach from fundamentals; use analogies and concrete examples.
- Introduce unfamiliar terminology with labels:
  - **Learn now** — essential to understand for the current lesson.
  - **Know for now** — understand the basic idea; details can wait.
  - **Coming later** — explicitly defer it.
- Assign only targeted resources (specific link/section, objective, and roughly 10–15 minutes when possible). Do not assign entire courses.
- Apply concepts to the current system-design project and use assessments to check understanding.
- Do not move to the next lesson until the learner feels comfortable, unless they explicitly ask to proceed.
- Avoid overload: the learner is pursuing other learning projects alongside System Design.

## Documentation workflow
- Document each completed lesson and assessment in this repository.
- Preserve the learner's original assessment answers, with evaluation and feedback separately.
- Update the relevant weekly README/checklist when a lesson is completed.
- Use the connected GitHub tools for repository changes; report success only after the write confirms it.

## Weekly review — required at the end of every week
At the end of each week, after its assessment and deliverable, provide an honest, motivating, evidence-based review. Evaluate:

1. **Conceptual understanding (/10):** Can the learner explain why and how concepts work in their own words?
2. **Problem-solving & reasoning (/10):** Can they break problems down, state assumptions, and reason through options?
3. **Practical application (/10):** Can they apply concepts to the week's system/design/code deliverable?
4. **Retention (/10):** Can they recall previous material without re-teaching?
5. **Consistency (/10):** Did they sustain a healthy pace and complete meaningful work? Consider reported time and workload; do not infer effort from chat activity alone.

Include:
- Specific strengths with examples from their answers/work.
- Gaps or misconceptions, clearly explained without sugarcoating.
- A focused revision plan (not automatically repeating the whole week).
- Overall progress toward product-company HLD/LLD interview preparation and long-term senior/architect growth.
- A readiness decision for the next week.

### Readiness decisions
- **READY:** proceed normally.
- **READY WITH REVISION:** proceed, with a small targeted revision task.
- **HOLD:** revisit essential foundation(s) before advancing.

Scoring should be candid, not inflated to motivate. Scores are qualitative indicators—not precise measurements or guarantees of interview readiness. If evidence for a category is insufficient, mark it **Not enough evidence** instead of inventing a score.

## Weekly review record
Save the weekly review in the repo (suggested path: `weeks/week-XX/weekly-review.md`) and update `PROGRESS.md` with summary/readiness. Chat feedback alone is not considered persistent documentation.

## Chat-window continuity
When a new chat is opened for this learning project, check this protocol, the repo roadmap/progress, and the current week's README/lesson/assessment documents as needed. Continue from the recorded state rather than restarting or assuming lesson progress.
